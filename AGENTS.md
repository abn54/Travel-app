# Project instructions

Keep `frontend/` (Vue) and `backend/` (FastAPI) separate. Part 2 uses SQLite for every application read and write. The backend seeds a brand-new `travel.db` once from the four supplied CSV files, preserves their text IDs, and never reloads the starter rows on a later startup. Open supplied CSVs with `utf-8-sig` because their first header contains a UTF-8 byte-order mark. All search, create, history, cancel, and delete actions must pass through FastAPI. Run the smoke test in `prompts/start-up-prompts.md` after relevant changes. Keep README, docs, prompts, handoff, and report evidence aligned with tested behavior.

For Assignment 1 Part 2 MVC, keep request models in `backend/models.py`, SQLite schema and seed responsibilities in `backend/database.py`, SQLite query and CRUD work in `backend/travel_controller.py`, and thin FastAPI request/response mapping in `backend/api_routes.py`. Keep `backend/app.py` limited to application setup. Vue is the View and must not access SQLite or CSV files directly.

For Assignment 2 Part 1, Vue is the view: it owns only UI state and renders the nearby-hotel list and Leaflet map. FastAPI is the controller: its route maps safe HTTP responses and calls the backend-only discovery controller. `backend/hotel_discovery_controller.py` is the model-facing integration: it resolves the exact U.S. ZIP first, requests Geoapify `accommodation.hotel` places in a 5 km circle around that returned center, and normalizes only provider-backed fields. Keep the Geoapify key in the project-root `.env`; never expose it to Vue. Do not add prices, ratings, availability, or booking claims to live provider results.

For the Part 1 verification loop, mock valid, invalid, unresolved, no-result, and provider-failure controller paths before using the live service. Then record one live ZIP, date, expected outcome, and observed outcome. Verify a list click selects the matching marker and a marker click selects the matching list item. Treat a provider failure differently from a successful search with no nearby results.

For revised Assignment 2 Part 2, preserve the Part 1 ZIP/list/map behavior. `backend/local_hotel_controller.py` owns saved provider locations and clearly labeled simulated course nightly-rate and room data in SQLite. `backend/hotel_chat_controller.py` owns the backend-only LLM workflow: OpenAI SQL proposal, strict read-only validation, SQLite retrieval, then a second grounded answer. `backend/api_routes.py` remains the thin HTTP controller, and Vue only renders local storage and chat state. Never expose an LLM key to Vue. Reject every non-SELECT, unbounded, unapproved-table, multi-statement, or write-like SQL proposal before SQLite execution. Verify a successful grounded answer, a successful no-match answer, a mocked provider failure, and a rejected write proposal.

For the RAG Context activity, `backend/hotel_chat_controller.py` uses OpenAI only on the backend. Load the versioned prompt at `prompts/hotel-assistant.md` during FastAPI startup. Save each conversation step in `conversation_messages` with message ID, conversation ID, timestamp, role, content, and a clear stage. Keep OpenAI-generated assistant messages distinct from FastAPI/SQLite tool records. The SQL retrieval must remain a bounded, read-only query over only `saved_hotels`, `saved_hotel_zips`, and `demo_hotel_nights`; conversation writes are separate from this read-only query. Preserve the existing local-hotel tables and frontend behavior while mirroring saved ZIP context for the RAG JOINs.
